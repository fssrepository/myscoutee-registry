1. Purpose and Safety Boundary

This manual explains the supported operator path for one independently governed MyScoutee Registry 1.0.0 instance on a standalone Linux host or virtual machine. The installed service accepts signed MyScoutee deployment records, protects an append-only SQLite history, and exposes registry-signed evidence over HTTPS.

In scope

  • installation from the released Debian package;
  • the separate Registry and Nginx production containers managed by systemd and Docker Compose;
  • immutable registry scope, Ed25519 registry identity, VOPRF keyring, TLS, and persistent SQLite state;
  • host qualification, independent public verification, monitoring, local administrative commands, backup, restore, incidents, and removal;
  • controlled artifact delivery and explicit trust pinning.

Out of scope

  • multi-node operation, automatic failover, cross-registry synchronization, or active-active SQLite;
  • unattended Registry self-update or a public MyScoutee APT repository;
  • building production artifacts on the operator host;
  • automatic repair of inconsistent signed or append-only state;
  • legal, tax, payment, acquisition, or beneficial-owner decisions.

Technical evidence is not payment authority

Registry settlements, reviews, ownership transfers, and exit allocations are signed technical records. They do not execute payments, create invoices, decide tax treatment, or replace external legal approval.

3. Architecture and Trust Model

Nginx service

Terminates TLS, redirects HTTP to HTTPS, enforces body, connection, and request-rate limits, and forwards to the Registry over the internal Docker network.

Registry service

Runs the non-root scratch Go image, verifies signed requests and state integrity, signs receipts and public evidence, and writes only to the protected data bind mount.

Persistent state

/var/lib/myscoutee-registry/data contains SQLite, the generated Registry signing key, and the VOPRF keyring. These files form one recovery unit.

Protected configuration

/etc/myscoutee-registry/registry.env and /etc/myscoutee-registry/tls/ hold host-specific configuration and TLS material. They are never release payload secrets.

Three independent trust checks

  1. Release trust: authenticate the Debian artifact through its Ed25519 release metadata and a full SPKI fingerprint obtained out of band.
  2. Transport trust: validate the HTTPS certificate chain, hostname, validity period, and final origin without insecure TLS or redirect following.
  3. Registry identity trust: verify the self-signed identity response, derive its rkey_… key ID, and pin the approved origin, scope, and registry key independently of TLS.

A valid TLS certificate does not establish the expected Registry signing identity. A valid Registry self-signature proves possession of the advertised key but does not prove that the endpoint is the intended deployment. Both checks and the out-of-band pin are required.

Scope is permanent identity domain separation

REGISTRY_SCOPE is recorded with the Registry identity on first start and is included in signed protocol state. A different scope represents a different sovereign namespace. Changing the environment value against an established database must fail startup; it is not a rename procedure.

5. Release Artifacts and Authenticity

The version 1.0.0 operator release is delivered as GitHub Releases assets, not through a MyScoutee APT repository. The operational payloads are:

  • myscoutee-registry_1.0.0_amd64.deb;
  • myscoutee-registry-client-tools_1.0.0.tar.gz;
  • publisher-supplied release metadata and an Ed25519 public key.

The package builder creates the Debian package and client-tools archive. The Debian package carries a byte-identical copy of that versioned archive at /usr/share/myscoutee-registry/myscoutee-registry-client-tools_1.0.0.tar.gz; it does not install expanded client scripts on the Registry host. Publisher signing is a separate release-authority step. The client tool verify-release.sh accepts one artifact, the release manifest, the release public key, and the independently trusted full SPKI fingerprint. It verifies:

  • canonical Ed25519 SPKI encoding and the complete sha256: fingerprint;
  • the deterministic pkey_… signing key ID;
  • artifact filename, purpose, version, byte size, and SHA-256 digest;
  • the Ed25519 signature over the canonical artifact metadata domain.
./verify-release.sh \
  myscoutee-registry_1.0.0_amd64.deb \
  /secure/release-manifest.json \
  /secure/release-public-key.pem \
  sha256:<64-lowercase-hex-characters>

A co-located key is not a trust anchor

Do not trust a release key merely because it was downloaded beside the package. Obtain and compare the complete SPKI fingerprint through an independent authenticated channel. Refuse any artifact for which signed release verification cannot be completed.

The Debian package embeds both production image archives. During package configuration, their archive SHA-256 values and portable content fingerprints are verified before the images are accepted. The package contains no production environment, TLS private key, Registry signing key, VOPRF seed, or SQLite database.

6. Standalone VM Installation

6.1 Direct host installation

  1. Verify the downloaded package as described in §5.
  2. Install it through local APT so Docker and Compose dependencies can be resolved.
  3. Review and replace every deployment-specific placeholder before the first start.
  4. Provision the TLS certificate and private key at the configured paths.
  5. Start explicitly, run host qualification, then run the external verifier from another trust boundary.
sudo apt install ./myscoutee-registry_1.0.0_amd64.deb

sudoedit /etc/myscoutee-registry/registry.env
sudo install -o root -g root -m 0600 /secure/fullchain.pem \
  /etc/myscoutee-registry/tls/fullchain.pem
sudo install -o root -g root -m 0600 /secure/privkey.pem \
  /etc/myscoutee-registry/tls/privkey.pem

sudo systemctl start myscoutee-registry
sudo /opt/myscoutee-registry/packaging/scripts/qualify-deployment.sh \
  check --expected-version 1.0.0 --timeout-seconds 60

Package installation deliberately does not start the Registry

The package loads and verifies both images, creates protected directories, and enables the systemd unit. It does not start or restart the Registry and does not run the external verifier. This prevents the placeholder scope, hostname, or TLS paths from becoming the first-start identity.

6.2 Remote client-tools flow

Obtain the separately released myscoutee-registry-client-tools_1.0.0.tar.gz, verify it, and extract it on the administrative client. A host that already has the Debian package installed also exposes the same archive bytes at /usr/share/myscoutee-registry/myscoutee-registry-client-tools_1.0.0.tar.gz for controlled retrieval. Do not run client wrappers from the Registry host. Copy install.env.example from the extracted archive to the gitignored install.env, restrict it to mode 0600, and configure SSH transport and release verification.

cp install.env.example install.env
chmod 0600 install.env
./install.sh /path/to/myscoutee-registry_1.0.0_amd64.deb

START_SERVICE=false is the default. For a fresh host, an explicit START_SERVICE=true requires all three validated local inputs together: DEPLOYMENT_ENV_FILE, TLS_CERTIFICATE_FILE, and TLS_PRIVATE_KEY_FILE. The wrapper transfers them through a protected temporary directory, installs root-owned configuration/TLS files, and then runs the package-provided restart-and-check qualification action. The actual install.env, deployment environment, and TLS files are gitignored and excluded from release artifacts.

The client-tools archive contains:

  • install.sh, install.env.example, and deployment.env.example;
  • remote-transport.sh and forward-localhost.sh;
  • verify-release.sh and the separate verify-deployment/ verifier;
  • purge.sh for an explicit destructive package purge.

External verification is never folded into installation

The remote installer can print the command for the requested public URL, but it does not execute it. Run that command separately from the client after the host installation and host qualification have completed.

6.3 Retrieve client tools and open an SSH tunnel

An authorized Registry operator with SFTP access can download the exact version-matched client-tools archive from an already installed host to an administrative workstation. Use the workstation's approved SSH configuration; do not place a password or private-key content in the command:

sftp registry-host
sftp> get /usr/share/myscoutee-registry/myscoutee-registry-client-tools_1.0.0.tar.gz ./myscoutee-registry-client-tools_1.0.0.tar.gz
sftp> bye

SFTP provides transport, not release authenticity. Authenticate the downloaded archive against the release metadata and independently pinned release-key SPKI fingerprint described in §5 before extraction. Then extract and run the helpers only on the workstation:

mkdir -m 0700 registry-client-tools-1.0.0
tar -xzf myscoutee-registry-client-tools_1.0.0.tar.gz \
  -C registry-client-tools-1.0.0
cd registry-client-tools-1.0.0

cp install.env.example install.env
chmod 0600 install.env
./forward-localhost.sh

Use the extracted verify-deployment/run.mjs from the workstation for the separate external check. Never extract or execute install.sh, forward-localhost.sh, or the verifier on the Registry server. SSH tunnel authentication does not replace public TLS validation or the expected Registry scope/key pin.

First-start lock-down

After the first successful start and after recording the Registry identity, set both generation switches to false. Restart and qualify so loss of the data directory fails closed instead of silently creating a new identity:

sudoedit /etc/myscoutee-registry/registry.env
sudo systemctl restart myscoutee-registry
sudo /opt/myscoutee-registry/packaging/scripts/qualify-deployment.sh \
  check --expected-version 1.0.0 --timeout-seconds 60

The release uses a bind mount at /var/lib/myscoutee-registry/data, not a disposable container layer. The directory is owned for container UID/GID 65532 and must not be manually edited. SQLite uses WAL, foreign keys, full synchronization, serialized access, append-only triggers, and integrity verification. A failed identity, chain, signature, direct-row, Merkle, or checkpoint check must fail closed.

8. DNS, TLS, Firewall, and Time

DNS and TLS

  • Use one stable hostname covered by the certificate. A Registry base URL is an origin, not a path, query, fragment, or credential-bearing URL.
  • Nginx accepts TLS 1.2/1.3, disables session tickets, adds HSTS and X-Content-Type-Options: nosniff, and redirects HTTP to the configured HTTPS hostname and port.
  • The Registry container remains plain HTTP on the internal Docker network and publishes no host port. Nginx is the only host-facing service.
  • Replace the certificate and key as one protected pair, restart Nginx through systemd, and verify the public chain and hostname normally. Do not use -k.
sudo systemctl restart myscoutee-registry

openssl s_client \
  -connect registry.example.com:443 \
  -servername registry.example.com \
  < /dev/null

curl --fail --show-error https://registry.example.com/versionz

Monitor UTC synchronization continuously. If the host clock is wrong, stop signed writes, correct the approved time source, restart and verify. Never rewrite accepted timestamps in SQLite.

9. Host Qualification and External Verification

9.1 Package-provided host qualification

The host qualifier validates the installed package version, two-image manifest, portable image content fingerprints, configured image references, systemd state, container image references and health, and the local TLS/Nginx path’s version, health, and identity consistency. It uses the configured certificate and hostname without exposing the Registry backend on a host port.

sudo /opt/myscoutee-registry/packaging/scripts/qualify-deployment.sh \
  check --expected-version 1.0.0 --timeout-seconds 60

Use restart-and-check only when an explicit restart is part of the approved action. Host qualification validates the configured certificate and local Nginx route, but it does not prove public DNS, external routing, or the expected business trust pin.

9.2 Separate external deployment verifier

Run the URL-driven verifier from the client side after the deployment is already running:

node verify-deployment/run.mjs \
  --url https://registry.example.com \
  --expected-version 1.0.0 \
  --expected-scope production:primary \
  --expected-key-id rkey_0123456789abcdef0123456789abcdef

The verifier is a manual operator command, not an automated E2E test, post-install hook, or aggregate test-runner member. It never starts or changes the deployment. It sends exactly one unauthenticated GET to each of:

  • /versionz — exact service, build version, and protocol version;
  • /v1/registry/identity — canonical Ed25519 SPKI, deterministic key ID, self-signature, and immutable scope;
  • /healthz — integrity status, scope/key consistency, ledger extent, and head invariants.

It requires an HTTPS origin, follows no redirects, refuses insecure TLS configuration, bounds response bodies, and performs no retries. For a private CA, extend normal Node trust with NODE_EXTRA_CA_CERTS. The --allow-http option is restricted to localhost or a literal loopback address for an intentional tunnel/VM test and cannot weaken a production URL.

Health is not a cheap ping

/healthz performs integrity work. Do not wrap the external verifier in a high-frequency monitor or retry loop. Use it for commissioning, release acceptance, and deliberate integrity checks.

9.3 Commissioning record

  • Debian package version, SHA-256, release-signing key ID, and full pinned release-key SPKI fingerprint.
  • Both production image references and installed content fingerprints.
  • Host/kernel/Docker/Compose versions, filesystem, time status, firewall rules, and public origin.
  • Certificate chain and expiry.
  • Exact registry_scope, registry_key_id, full Registry SPKI fingerprint, and identity response.
  • Initial ledger index, entry count, and head hash.
  • Host qualification result and separate external verifier result.
  • Backup destination and clean-host restore schedule.

12. Backup and Restore

Complete recovery unit

Back up these items together under one evidence ID:

  • every file under /var/lib/myscoutee-registry/data, including SQLite/WAL/SHM when present, Registry signing key, and VOPRF keyring;
  • /etc/myscoutee-registry/registry.env and the TLS certificate/private-key pair under their custody policy;
  • installed package version, package hash/signing evidence, image content fingerprints, and host/platform record;
  • Registry identity, latest health head, selected checkpoints/Merkle evidence, and backup checksums.

Raw copy requires quiescence

The release has no Registry-native backup command, and the scratch runtime has no shell or SQLite utility. Do not copy a changing database, WAL, and SHM sequentially. Stop the service, use a separately qualified SQLite online-backup tool, or take an atomic storage snapshot.

Quiesced backup

  1. Record UTC time, package/image identity, public identity, ledger head, and service state.
  2. Stop public ingress and run sudo systemctl stop myscoutee-registry.
  3. Confirm the exact bind directory /var/lib/myscoutee-registry/data; never guess another path.
  4. Take an atomic snapshot or root-controlled archive preserving numeric UID/GID, modes, timestamps, and every file.
  5. Back up configuration, TLS, and release evidence under the same backup ID.
  6. Encrypt, checksum, store, and independently verify the backup.
  7. Restart, run host qualification, and verify the public identity/head.

Clean-host restore

  1. Isolate the target from client traffic and install the exact recorded Debian release without starting it.
  2. Restore the complete data directory with numeric owner 65532 and original modes.
  3. Restore protected configuration and TLS with the original scope. Keep generation switches false.
  4. Start the service and preserve startup logs. Integrity, key, scope, and state mismatch must fail.
  5. Run host qualification, then compare /versionz, identity, health, ledger head, and selected proof evidence with the backup record.
  6. Run the external verifier and restore traffic gradually.

A replacement generated key or an empty healthy ledger is not recovery. Restore drills must be performed on an isolated clean host at the frequency required by the local RPO/RTO.

13. Reinstall, Future Update, and Rollback

The Registry has no self-updater. Its announcement feed concerns MyScoutee deployment packages; Registry package replacement is an explicit host-administration action.

Same-version reinstall

A 1.0.0 reinstall refreshes the package payload while preserving configuration and state. Package configuration still does not restart an active Registry. The client wrapper uses a controlled dpkg --unpack plus APT dependency repair for this case and restarts only when explicitly requested.

Future release acceptance

  1. Authenticate the new Debian artifact and client tools through their release-signing evidence.
  2. Review release notes, state-format changes, image contents, Nginx policy, protocol changes, and release qualification.
  3. Take and verify a complete pre-change recovery-unit backup and rehearse it on an isolated host.
  4. Schedule downtime or drain ingress; install without assuming package configuration restarts the service.
  5. Explicitly restart, run host qualification, and compare scope, Registry key, ledger head, public TLS, representative reads, and proofs.
  6. Run the separate external verifier and retain the prior backup until the observation window closes.

Rollback is a recovery decision

If a future binary has changed persistent state, do not simply start an older image against that state. Restore the complete pre-change database/key/keyring/configuration unit with the corresponding released package unless that exact downgrade path was explicitly qualified.

14. Security Operations and Incidents

Preventive controls

  • least-privilege host/Docker access, MFA on infrastructure control planes, a restricted management network, and privileged-command audit;
  • mode-0600 configuration and keys, no symlink substitution, encrypted backups, and no production secrets in artifacts or source;
  • pinned release metadata, full release-key SPKI fingerprint, pinned Registry identity, controlled TLS renewal, and reliable UTC time;
  • external retention of selected identity, checkpoint, and Merkle evidence;
  • no manual SQLite UPDATE/DELETE, nonce pruning, or query-table repair;
  • controlled distribution of Registry binaries and artifacts because exposure increases reverse-engineering, vulnerability-response, provenance, and patch-coordination risk even though security must not depend on binary secrecy.

15. Retirement and Removal

  1. Freeze new enrollment and notify bound client operators through a trusted channel.
  2. Complete signed deactivation/disconnect where required while the original Registry identity is still available.
  3. Finalize required checkpoints, export agreed evidence, and verify a complete final backup on an isolated host.
  4. Stop the service and revoke public DNS/TLS/firewall exposure.
  5. Apply the approved retention/destruction policy to state, keys, TLS, configuration, logs, images, packages, and backups.

Package removal versus purge

apt remove myscoutee-registry stops/disables the stack but preserves host configuration and state. apt purge myscoutee-registry is deliberately destructive: it removes Registry configuration, TLS material, SQLite state, Registry/VOPRF keys, installed payload, and the configured managed images. Independently stored backups are not removed.

Purge is irreversible without a verified backup

Do not use the client purge.sh helper as a troubleshooting shortcut. Obtain explicit authorization, verify the exact target and final backup, and record what will be destroyed before running it.
